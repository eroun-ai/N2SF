## 2. 역할 구분

이 제안서는 pii-ner-x를 확인하지 못한 상태에서 작성되었습니다. 검토 시 두 영역을 구분해 주십시오.

| 영역 | 소관 | 이 제안서에서의 상태 |
|---|---|---|
| **판별 기준**: 무엇을 개인정보로 보는가 (엔티티 종류, 라벨 체계, 탐지 규칙, 이름·주소 판별, 오탐 기준, 출력 라벨) | **pii-ner-x** | 각국 법령을 근거로 작성한 임시 내용. pii-ner-x 기준으로 교체 대상 |
| **판정 구조**: 어떻게 빠르고 정확하게 판정하는가 (계단식 구조, Clef 질문 설계, 디코더 제외, 정책 엔진 분리, 적용 지점 연동) | **이 제안서** | 검토 요청 대상 |

판별 기준은 pii-ner-x 기준을 따르는 것으로 확정되어 있으며, 제안서 서두와 5장에 같은 내용을 명시했습니다.

## 3. pii-ner-x 기준으로 교체할 절

|---|---|---|
| 5.1절 코드 규칙 | `{법역}.{대분류}.{세부유형}` 형식, 대분류 10개 | pii-ner-x 라벨 체계로 교체 |
| 5.2절 법역별 엔티티 | 한국·일본·미국·사우디 식별번호와 민감정보 목록 | pii-ner-x 라벨 목록으로 교체, 법역 대응 관계만 유지 |
| 5.3절 이름·주소 판별 | pii-ner-x 기준을 따른다고만 명시 | pii-ner-x의 이름·주소 라벨, 탐지 규칙, 오탐 기준, 주소 상세도 기준 반영 |
| 4.1절 후보 생성 | 정규식·검증식·사전 예시 | pii-ner-x 탐지 규칙으로 교체 |
| 4.2절 Clef 선택지 | 대분류 → 세부 유형 2단계 | pii-ner-x 라벨로 대분류와 세부 유형 구성 |
| 4.7절 값 종류 구분 | 실제값 / 예시값 / 마스킹됨 / 자리표시자 | pii-ner-x에 같은 기준이 있으면 교체 |
| 6.2절 정책 표의 엔티티 그룹 | 고유식별·민감·금융·연락처 등 8개 그룹 | pii-ner-x 라벨 기준으로 다시 매핑(조치 열은 유지) |
| 7장 결과 JSON | `code`, `label`, `category` 등 | pii-ner-x 출력 형식과 필드명 일치 |
| 도식 HTML의 엔티티·정책 표 | 위와 동일한 임시 내용 | 제안서 교체 후 함께 갱신 |

## 4. 확인 전 초안으로 표시한 항목

| 항목 | 위치 | 요청 사항 |
|---|---|---|
| 직무 수행 공무원 성명 구분 | 5.4절, 6.2절 마지막 행 | pii-ner-x에 공무원 성명 처리 기준이 있는지 확인. 없다면 초안(직무 수행 문맥 + Clef 역할 판정 + 민감정보 결합 여부, 기관별 설정, 기본값은 일반 성명과 동일)의 채택 여부 검토 |

초안의 판단 원칙은 "그 사람이 공무원인가"가 아니라 "이 문서에서 직무를 수행한 사람으로 등장하는가"입니다. 직원 명부 대조만으로는 징계·병가 문서 속 직원, 동명이인, 다른 기관 공무원을 구분할 수 없으므로 문맥 판정을 함께 사용합니다.

## 5. 검토 질문

**pii-ner-x와 판정 구조의 결합**

1. pii-ner-x에 학습된 NER 모델이 포함되어 있습니까? 포함되어 있다면 제안서 4.5절의 "Clef 증류 인코더 태거"를 pii-ner-x 모델로 대체할 수 있는지 검토가 필요합니다. 대체하면 인코더 증류 학습 단계가 불필요해집니다.
2. pii-ner-x 라벨 수는 몇 개입니까? Clef의 `choice` 질문은 선택지가 최대 255개이며, 제안서는 정확도를 위해 대분류(약 10개)와 세부 유형(5~20개)으로 나누어 질문합니다. pii-ner-x 라벨이 이 2단계 구조로 묶일 수 있는지 확인이 필요합니다.
3. pii-ner-x의 탐지 결과는 문자 위치(오프셋)를 제공합니까? 제안서는 원문 좌표를 결과에 포함하며, 정규화(전각·아랍 숫자 변환 등) 전후의 위치 대응표를 유지합니다.
4. pii-ner-x는 한국 외 법역(일본, 미국, 사우디아라비아)과 일본어·아랍어 문서를 지원합니까? 지원 범위가 다르면 법역별로 기준 출처를 나누어야 합니다.

**판별 기준과 정책의 경계**

5. pii-ner-x는 "개인정보인가"까지만 판단합니까, 아니면 "차단할 것인가"(조치)까지 정의합니까? 제안서는 조치를 정책 엔진(규칙 테이블)에서 결정합니다. pii-ner-x에 조치 기준이 있으면 정책 엔진의 입력으로 사용합니다.
6. 결합 식별성(생년월일+성별+직급 등 준식별자 조합)에 대한 기준이 pii-ner-x에 있습니까? 제안서 4.6절은 열 단위 판정과 고유값 비율 계산을 제안합니다.

## 6. 포크 판단 기준

| 항목 | pii-ner-x 확장이 적합한 경우 | 새 프로젝트 분리가 적합한 경우 |
|---|---|---|
| 실행 환경 | pii-ner-x를 Linux·CUDA 서버에서도 운용할 계획이 있음 | pii-ner-x는 맥북(Apple Silicon) 중심으로 유지하고, 제품은 24GB GPU 서버에서 운용 |
| 모델 의존성 | Clef-flash(9B) 서빙을 pii-ner-x에 추가해도 개발·배포 부담이 적음 | pii-ner-x를 경량 규칙·NER 도구로 유지하려 함 |
| 기능 범위 | 문서 해체(HWP·OCR), 정책 엔진, 적용 지점 연동까지 pii-ner-x 범위로 볼 수 있음 | pii-ner-x는 판별 라이브러리, 제품은 망간전송·AI 입력 통제·저장소 점검과 연동하는 서비스로 구분 |
| 배포 주기 | 판별 기준과 제품 기능을 같은 주기로 배포해도 무방 | 고객사별 설치·인증 일정에 따라 제품 배포 주기가 따로 필요 |

**권장안**: 새 프로젝트를 분리하더라도 **판별 기준은 pii-ner-x 한 곳에서만 관리**하고, 새 프로젝트는 pii-ner-x를 패키지 또는 하위 모듈로 참조하는 구조를 권장합니다. 판별 기준이 두 저장소로 나뉘면 같은 문서에 대해 두 제품의 판정이 달라질 수 있기 때문입니다. 예를 들어 pii-ner-x에서 주소 상세도 기준을 바꾸었는데 포크한 프로젝트에 반영되지 않으면, 같은 민원서류가 한쪽에서는 허용되고 다른 쪽에서는 차단됩니다.

참고: 검색 결과에서 Clef-flash를 Core ML 형식으로 변환한 공개 저장소(`mlboydaisuke/clef-flash-CoreAI`)가 확인되었습니다. 맥북 환경에서의 Clef 실행 가능성을 판단할 자료가 될 수 있으나, 내용과 품질은 확인하지 않았습니다.

## 8. 회신 요청

1. 3장 교체 대상 절별로 대응하는 pii-ner-x 기준(파일 또는 문서 위치)
2. 4장 공무원 성명 초안의 채택·수정·폐기 의견
3. 5장 검토 질문에 대한 답변
4. 6장 기준에 따른 확장·분리 결정

회신을 받으면 제안서 5~7장과 도식을 pii-ner-x 기준으로 갱신합니다.
